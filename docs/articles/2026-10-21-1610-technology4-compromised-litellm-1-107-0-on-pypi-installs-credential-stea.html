Poisoned LiteLLM Release Steals Every Key a Developer Owns, Politely

Version 1.107.0 of a popular AI gateway package carried a credential stealer and backdoor that ran in every Python process, according to security firm SafeDep.

The wire said: Compromised LiteLLM 1.107.0 on PyPI Installs a Credential Stealer and Backdoor · Hacker News

By The Daily Spin Desk · TechnologyOct 21, 2026 16:10 UTC · 3 min read

Catch up

LiteLLM is an open-source Python library that lets developers talk to many AI model providers through one interface. A security analysis published on Hacker News says version 1.107.0, uploaded to PyPI, the main Python package repository, contained malware that is absent from the public source code.

Why it matters

Anyone who installed 1.107.0 should assume that SSH keys, cloud logins and AI provider keys on that machine were exposed, and rotate them. The case also shows that a clean public repository does not guarantee a clean package.

The LiteLLM 1.107.0 release on PyPI contained a credential stealer and a remote code execution backdoor, according to an analysis hosted on Hacker News and attributed to SafeDep. All seven wheels, the prebuilt installers for Linux, macOS and Windows, carried the payload. PyPI has since removed the release. The upstream GitHub source never contained the malicious files, which is a bit like a restaurant passing inspection while a second kitchen operates in the basement.

Translation: a wheel is a ready-to-install package, and a .pth file is a Python configuration file that can also run code at startup. The attackers used both. Installing the package placed three files in site-packages: cook.pth, cook.py and sitecustomize.py. Python loads the first two every time it starts, on any host where the package is present, even in programs that never import litellm. Installing it was not required to be a user of it, merely to be near it.

The stealer, cook.py, hunted for a thorough list: SSH keys, cloud credentials for AWS, Azure and Google, Kubernetes configs, CI/CD secrets, browser passwords, shell history, and tokens for AI tools including Claude Code, Cursor, Copilot and Codex. On a LiteLLM proxy it also dumped database tables that hold the LLM provider keys. It encrypted the haul and posted it to a lookalike address, www.litellm[.]dev, at a path called /healthcheck. The name is the most reassuring part of the operation.

The second file, sitecustomize.py, started a background daemon. Every hour, SafeDep says, it read a server address from a file on GitHub, ran the stealer again and downloaded and executed whatever code that server supplied. Translation: backdoor means the attacker could change the instructions later, so the damage was not limited to the first theft.

How the code got in is the interesting part. The source distribution had a single extra line in its build configuration, data = "cook", telling the build tool to copy a hidden cook/ folder into the wheel. The folder itself was left out of the source package, so the line was the only visible clue. No public commit in BerriAI's repository contains either one.

The release also did not match its own tag. According to SafeDep, the tag v1.107.0 pointed to a commit whose version file said 1.108.0. The published package matched a later commit, with the version rewound to 1.107.0 and the companion dependency pins set to the values from a release candidate. The effect was that a comparison against that candidate showed nothing odd. The attacker, in other words, tidied up.

Clues in the wheels suggest the real release machinery was used. The wheels name the same build tool version as legitimate releases, and the timestamps show separate native builds for macOS, Linux and Windows. SafeDep checked all 539 public GitHub Actions runs between 09:30 and 12:30 UTC and found none that built or published the release. It concluded, with moderate to high confidence, that BerriAI's private pipeline built the wheels from attacker-modified source. A stolen PyPI token used from the attacker's own machines, it said, fits the evidence less well.

SafeDep does not claim to know the cause. It names possibilities: a compromised maintainer or bot credential, a private branch or mirror, or the reference the pipeline builds from. Only BerriAI's pipeline logs can settle it. Versions 1.106.2, 1.107.0rc1 and 1.107.0rc2 are clean, as are the two companion packages the release pins.

For anyone who installed 1.107.0, the practical advice follows from the target list: treat every secret on the machine as read, and replace it. The malware writes a marker file in /tmp so it collects only once per host, which is considerate, though not to the host. Watch for BerriAI's own account of how its pipeline ended up building somebody else's code.
