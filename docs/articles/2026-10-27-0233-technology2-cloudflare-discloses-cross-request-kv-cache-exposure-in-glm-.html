Cloudflare Model Briefly Shares Customers' Long Prompts With Strangers, Returns Them Pre-Owned

A 155-response leak on Workers AI's GLM-5.3 traced to a memory pool smaller than the context window it advertised, and an engine bug that treated 'rejected' as 'proceed anyway.'

The wire said: Cross-request KV cache exposure in the GLM-5.3 Workers AI model (155 responses) · Hacker News

By The Daily Spin Desk · TechnologyOct 27, 2026 02:33 UTC · 2 min read

Catch up

Cloudflare disclosed that between August 27 and September 9, 2026, some customers of its GLM-5.3 model on Workers AI received text belonging to other customers' sessions. A security researcher reported it on September 8, and the model was restored the next day after fixes.

Why it matters

Anyone sending sensitive material to a shared AI service is relying on the provider to track whose data sits in which piece of GPU memory. This incident shows how a small configuration gap can quietly break that promise, though only for extremely long prompts.

Cloudflare said on its blog that 155 responses from its GLM-5.3 model on Workers AI contained data from other customers' requests. All affected prompts were longer than 681,280 tokens. Translation: a token is roughly a word fragment, so these were enormous inputs, the sort of thing you send when you paste in an entire codebase and hope for the best.

According to Cloudflare, a security researcher, Gadi Evron of Knostic, reported the problem on September 8 through its HackerOne program. The company reproduced it the next morning, took the model offline within 40 minutes of declaring an incident, and restored service on September 9. It says no other Workers AI model was affected, and that the issue began August 27.

The cause was two problems stacked on each other. First, Cloudflare deployed the model with a 1,048,576-token context window, meaning the amount of text it claims it can read at once. But the KV cache pool on its prefill GPUs had room for only 681,280 tokens. Translation: the KV cache is the model's short-term memory of your prompt, and the company had advertised a bigger desk than it had bought.

Cloudflare says it knew about the mismatch before launch. It expected the engine to return an error for any prompt that did not fit. Its long-context tests returned successful responses, so it concluded things were fine. The company's own postmortem admits that it checked HTTP status codes and speed but not whether the output made sense. A 200 OK, it turns out, is a statement about delivery, not content.

The second problem lived in SGLang, the open-source inference engine Cloudflare uses. When a prompt was too long, the engine marked it rejected and swapped in a one-token placeholder. Instead of stopping and sending the client an error, it carried on, built the cache for the placeholder, and shipped it to the decode node, which writes the response.

The decode node saw a 'transfer complete' message and assumed the new request's data had overwritten the old. It had not. Most of the memory pages still held other people's earlier requests, and the model generated its answer while looking at them. Cloudflare notes that pages are not zeroed between requests, which is common in inference engines and good for performance, and which makes the engine solely responsible for knowing who owns what.

Cloudflare says the requests it found, after excluding its own testing and the researcher's, matched ordinary long-context use in timing and volume. It found no evidence of deliberate exploitation. That is reassuring, though it also means the leak worked well enough without anyone trying.

The fixes are two-fold. Cloudflare changed its configuration so the pool holds about 2.04 million tokens, roughly twice the context length, so a valid prompt can never hit the rejection path. It also patched the engine so rejected requests are retired with their original error before any memory is allocated or transferred. SGLang's maintainers shipped related fixes, with the main fix landing in v0.5.21 according to the report.

Cloudflare also says it now checks pool size against context length directly on the running engine before any disaggregated deployment change. In other words, the company has begun verifying that the number on the box matches the number in the box.
