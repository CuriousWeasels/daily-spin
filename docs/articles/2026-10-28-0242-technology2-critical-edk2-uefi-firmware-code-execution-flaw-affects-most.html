Sixteen-Year-Old Bug in Server Boot Code Finally Introduced to Public, Along With Its Patch

A 9.5-severity flaw in the open source firmware code behind most servers leaked early, after a hardware maker published the fix before the coordinated disclosure.

The wire said: Code-execution flaw in UEFI firmware affects most servers on planet Earth · Ars Technica

By The Daily Spin Desk · TechnologyOct 28, 2026 02:42 UTC · 2 min read

Catch up

UEFI firmware is the code that runs when a computer starts, before the operating system and its security defenses load. A flaw in TianoCore EDK II, the open source codebase most firmware vendors build on, was meant to be disclosed in January but surfaced early.

Why it matters

Organizations that boot servers over a network now have a public roadmap to a flaw that can run attacker code before security tools wake up, and firmware patching across thousands of vendors is slow. Home users and anyone booting only from local disks are not affected, according to Ars Technica.

Ars Technica reported that a memory-corruption flaw, tracked as CVE-2026-97631, affects the firmware code used by most of the world's server vendors and data centers. It carries a severity rating of 9.5 out of 10. Translation: a bug in the software that starts the machine, which is the one moment when the machine is least able to defend itself.

The flaw sits in TianoCore EDK II, an open source codebase that firmware suppliers such as AMI, Insyde, and Phoenix use extensively. Ars noted that Microsoft's hardened fork, Project Mu, used the vulnerable component as well. A UEFI Forum representative once called EDK2 the "preeminent solution / implementation of the UEFI specifications," which is a reassuring thing to say until the next paragraph.

The bug is a 16-year-old buffer overflow in the PXE-Base Code driver, which lets devices boot from code downloaded over a local network. Translation: a buffer overflow means the software was handed more data than the space reserved for it and kept copying anyway. Here the driver reserves 504 bytes for ICMP error messages, and per the advisory it still copies longer messages past that limit. An attacker with low-level access to the local network can send one during network boot and corrupt the firmware.

Exploitation runs before Secure Boot and other defenses can act, and the code executes in ring 0, the most privileged level of a CPU. HD Moore of Dragos told Ars that an attacker could hijack program flow while the boot process still has access to sensitive parts like the TPM, potentially breaking disk encryption. The payload does not persist by itself, but it can open the door to others that do.

The disclosure did not go as planned. The researchers, Alex Matrosov of Anthropic and Dan Holmes of Google, had arranged coordinated disclosure for January. Ars reported that AMI published a pull request last month detailing the flaw and including a fix. TianoCore members then issued a public advisory last week. Translation: the plan was to keep the secret until everyone had a patch, and the patch announced the secret instead.

Publicly available patch code makes it easier for skilled attackers to see how the flaw is triggered and build exploits, and updating firmware across millions of devices from thousands of makers is slow. Moore said it is likely a "forever" bug that will linger in end-of-support systems. Ars also noted this came six days after another botched disclosure involving a critical PHP vulnerability.

There are limits. Attackers need some control over a local network, which points to insiders or intruders such as nation-states and ransomware operators who are already inside. Jesse Michael of Eclypsium told Ars that exploits must be tuned to each target's model, version, and configuration because memory addresses change. He added that, unlike some earlier Secure Boot bypasses, this one can be fixed with a basic code fix delivered as a BIOS or UEFI update, without key revocations.

UEFI has a long record of such flaws, including LogoFail, PixieFail, and PKFail. Researchers ran multiple fuzzing projects after PixieFail to find similar bugs in EDK2, and Ars said those efforts apparently missed this one for 16 years. The next thing to watch is how quickly vendors ship updates, which historically is measured in seasons rather than days.
